# Сервер синхронизации АрендаЛог

Общий доступ: арендодатель видит журнал в реальном времени, проживающие добавляют записи наравне
с арендатором. Без сервера приложение работает полностью офлайн — сервер нужен только для совместной работы.

Один файл, ноль внешних зависимостей: Node.js 18+, HTTP, файловое хранилище, SSE.

```bash
node server/sync-server.js 8788
# переменные: PORT, DATA_DIR, MAX_SPACE_MB, PUBLIC_URL
```

Слушает все интерфейсы — в продакшене ставить за обратный прокси с TLS (Android блокирует открытый HTTP).

---

## Модель доступа

| Роль | Кто получает | Права |
|---|---|---|
| `owner` | создатель пространства | читать, писать, приглашать |
| `write` | проживающие (по приглашению) | читать, писать события и метаданные |
| `read` | арендодатель (по приглашению) | только чтение и поток в реальном времени |

Приглашение выглядит как код:

```
https://sync.example.ru#a1b2c3d4e5f6a7b8:9f2c…(48 символов)
```

Слева — адрес сервера, после `#` — идентификатор пространства и токен. Токен хранится на сервере
только в виде SHA-256, восстановить его из базы нельзя.

## API

| Метод | Путь | Права | Назначение |
|---|---|---|---|
| POST | `/api/space` | — | создать пространство, получить токен и два кода |
| GET | `/api/space/:id` | read+ | метаданные, роль, размер |
| PUT | `/api/space/:id/meta` | write+ | зоны, проживающие, данные договора |
| POST | `/api/space/:id/invite` | owner | новый код на чтение или запись |
| POST | `/api/space/:id/events` | write+ | добавить события (идемпотентно по id) |
| GET | `/api/space/:id/events?since=N` | read+ | получить новое с сервера |
| GET | `/api/space/:id/stream?token=…` | read+ | SSE-поток изменений |
| POST | `/api/space/:id/blob` | write+ | загрузить вложение (заголовок `X-Sha256`) |
| GET | `/api/blob/:sha?space=…` | read+ | скачать вложение |
| GET | `/api/health` | — | состояние |

## Что сервер проверяет сам

- **Хеш каждого события** пересчитывается заново по канонической форме. Несовпадение не блокирует приём
  (данные важнее), но помечается в `serverCheck.hashOk = false` — клиент и отчёт это видят.
- **Непрерывность цепочки** по каждому автору: `prevHash` должен совпадать с последним хешем этого автора
  (`serverCheck.chainOk`).
- **Размер вложения** сверяется с заявленным `X-Sha256`.
- **Права**: токен чтения не может писать, приглашать может только владелец, без токена — 401.

Подписи ECDSA сервер не проверяет (нет открытых ключей всех авторов); это делает клиент и верификатор
пакета. Сервер — транспорт и защита от порчи, а не арбитр.

## Хранилище

```
data/
  spaces/<spaceId>.json     метаданные + события (текст)
  blobs/<sha256>            вложения, по одному файлу на уникальный хеш
```

- **Дедупликация**: одинаковый файл хранится один раз (ключ — SHA-256). Если фото попало в два события
  или его переслали с другого устройства — место не удваивается.
- **Запись атомарная**: временный файл + `rename`, база не побьётся при падении.
- **Сжатие**: ответы больше 1 КБ уходят gzip (события сжимаются в 3–4 раза). Фотографии не пережимаются
  осознанно: JPEG уже сжат, а повторное сжатие ухудшит качество доказательства.

## Сколько это стоит

### Сколько занимает один журнал

| Что | Объём |
|---|---|
| Фотография (1600 px, JPEG q0.82) | 150–400 КБ, в среднем ~250 КБ |
| Событие без фото (JSON + токен метки времени) | 6–8 КБ |
| Аренда на 11 месяцев: ~100 событий, ~200 фото | **≈ 50 МБ** |
| Активная аренда с 500 фото | ≈ 130 МБ |
| Текстовая часть всех событий | < 1 МБ |

То есть **98 % объёма — фотографии**, и именно они определяют требования к диску.

### Сколько нужно серверу

| Показатель | На 20 журналов | На 100 журналов | На 500 журналов |
|---|---|---|---|
| Диск (фото) | 1 ГБ | 5 ГБ | 25 ГБ |
| Трафик в месяц (3 устройства × новые фото) | ~3 ГБ | ~15 ГБ | ~75 ГБ |
| Процессор | простаивает | 1 vCPU хватает | 1–2 vCPU |
| Память | 512 МБ | 1 ГБ | 2–4 ГБ (кэш активных пространств) |

Пиковая нагрузка ничтожна: запись события — это добавление строки в массив и `fs.rename`, десятки
запросов в секунду держит любой VPS.

## Установка на VPS (по шагам)

```bash
# 1. Node.js 18+ и каталог
mkdir -p /opt/arendalog && cd /opt/arendalog
# скопировать server/ из проекта

# 2. запуск как службы
cat >/etc/systemd/system/arendalog.service <<'EOF'
[Unit]
Description=ArendaLog sync
After=network.target
[Service]
Environment=PORT=8788
Environment=DATA_DIR=/var/lib/arendalog
Environment=MAX_SPACE_MB=500
ExecStart=/usr/bin/node /opt/arendalog/server/sync-server.js
Restart=always
User=arendalog
[Install]
WantedBy=multi-user.target
EOF
systemctl enable --now arendalog

# 3. TLS через Caddy (проще всего)
caddy reverse-proxy --from sync.example.ru --to 127.0.0.1:8788

# 4. резервная копия
rsync -a --delete /var/lib/arendalog/ /backup/arendalog/
```

В приложении: «Ещё» → «Общий доступ» → адрес `https://sync.example.ru` → «Создать пространство».
Дальше приложению выдаются два кода — арендодателю и проживающим.

## Ограничения текущей версии

- Нет удаления событий на сервере (журнал append-only — это осознанно: удаление ломает доказательную базу).
- Нет лимита запросов на IP: за обратным прокси стоит включить rate limiting.
- Поиск и фильтры выполняются на клиенте: сервер отдаёт всё новое начиная с `since`.
- Токены не имеют срока действия; отзыв — правкой `tokens` в файле пространства.
